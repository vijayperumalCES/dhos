# ADR-0015: Delivery metrics and emailed weekly and monthly reports

**Status:** Accepted · 2026-11-07

## Context
Delivery teams report a fixed set of process metrics for every project each week (scope creep,
variances, test and UAT coverage, releases and rollbacks, retrospectives, customer satisfaction, AI
adoption: 30 in all). They are reported to the customer and to leadership, weekly and monthly,
by email. Some figures Stride already holds (releases, escalations, pull-request links, change
requests); most it does not.

## Decisions

1. **One value per project, metric and week (Monday).** `project_metric_entries` holds typed values.
   Counts, percentages and scores share one numeric column; the catalogue (`private.metric_catalogue()`)
   fixes each metric's allowed range and how weeks combine in a longer period: counts add up,
   percentages average, quarterly scores and open items take the latest week.
2. **Automatic where Stride knows, manual everywhere else, and manual wins.** Six metrics are filled
   from existing records when nobody enters a value: scope creeps (change requests raised), pull
   requests (links on work items), successful releases, and the three escalation figures. A manual value
   overrides the automatic one for the same period, so a team that counts differently can say so. An
   unreported metric is empty, never zero: only a count the system can compute is a true zero.
3. **"Agreed metrics reported (%)" is derived.** It is the share of the other 29 metrics that have a
   value in the period and cannot be typed in, so it cannot be gamed.
4. **No new permission; the whole team can enter values.** Figures come from different people (QA,
   UAT, engineering, delivery), so anyone *assigned to the project* may enter values, as may anyone with
   `project.change_status`; both must be able to read the project (`can_enter_metrics`). Each entry
   records who typed it, the form saves only the fields a person changed so teammates' values are never
   overwritten, and every change is audited. Setting recipients and seeing report history still need
   `project.change_status`, because recipients can be outside addresses. Reading the figures needs only
   access to the project. Nothing is written directly: three `SECURITY DEFINER` functions are the only writers.
5. **Reports are generated by a scheduled job, in the database.** `metrics_reports` (hourly) builds the
   last complete week and last complete month for each project that has recipients and a report switched
   on, and that is planning, active or on hold. One row per project, kind and period
   (`metric_report_runs`, unique), so a missed day, an overlapping run or an enabling mid-week is safe. The
   payload is a snapshot: later edits to the metrics do not change what was sent.
6. **Sending reuses the tick.** A new `reports` stage claims pending runs (`SKIP LOCKED` and a ten-minute
   lease), emails each recipient through the configured provider, and reports back. Delivery is tracked per
   recipient, so a retry after a partial failure sends only to those who have not got it; three attempts, then
   `failed`. Without `RESEND_API_KEY` a report is marked `simulated`, as for notification email. Claim and
   complete are `service_role` only.
7. **Recipients are a list on the project, not members.** Customers receive these reports, so addresses
   need not belong to anyone in Stride. Up to 20, normalized, validated in the database. The list and the
   history are visible only to people who can publish for the project; the audit entry records how many
   addresses, never which.
8. **Off by default.** No project emails anyone until a manager adds recipients and switches a report on.

## Consequences
- The email contains the project's figures, including for customers a manager adds. Managers see a warning
  where they enter addresses.
- A weekly report for a week with no entered values still goes out, showing only the automatic figures
  and "not reported" for the rest; the reported share makes the gap visible.
- A project that moves to completed or cancelled stops being reported from the next run.
- Not built: per-project schedule (fixed Monday and 1st), sending to members chosen by role, charts or
  attachments, a send-now button (use **Automation → Scheduler → run now**, which generates reports for
  periods not yet generated), importing values from CSV.
